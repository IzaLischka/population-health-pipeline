# Raw data source: Synthea synthetic patient records

## What this is

The `data/raw/synthea/` directory holds a pre-generated synthetic patient
dataset (FHIR R4 bundles) produced by [Synthea](https://synthetichealth.github.io/synthea/),
MITRE's open-source synthetic patient population simulator. All data here is
entirely synthetic: no real patient, encounter, or observation exists behind
any of these records. Synthea is the de facto standard tool for this in the
health data engineering space, so this dataset is representative of realistic
FHIR structure and clinical coding (SNOMED CT, ICD-10, LOINC) without any of
the privacy exposure of real health data.

## How it got here: manual download, not generation or API pull

This is a **manual, one-time download**, not an automated ingestion (API,
SFTP, streaming). That is a deliberate, documented trade-off, not an
oversight — other projects in this portfolio (see the repository index)
demonstrate automated ingestion patterns; this one demonstrates something
else instead: rigorous provenance and lineage tracking on a data source you
don't control the acquisition of, which is a routine situation in real
health data engineering (vendor drops, one-time regulatory extracts, data use
agreements that specify manual transfer).

### Why not generate it locally with Synthea?

The original plan was to run the Synthea CLI/jar locally to generate five
annual batches (2022–2026) with fixed seeds, for reproducible year-over-year
fixtures. In practice, this hit a known Synthea failure mode: for certain
seeds, a simulated patient's aging state machine fails to reach a terminal
"death" state and the simulation keeps advancing that one patient's
simulated age indefinitely (observed: a patient still "alive" at 357
simulated years). Because the seed is fixed, this is fully deterministic —
retrying with the same parameters reproduces the same runaway patient every
time.

A retry-with-alternate-seed fallback was implemented in
`scripts/generate_synthetic_data.py` (kept in git history for reference) to
work around this, but repeated multi-hour local generation runs on a
Windows/JVM setup were not a good use of time for what is meant to be a
lightweight development fixture. The pragmatic call: use MITRE's own
pre-generated sample datasets instead. They come from the same tool, contain
the same kind of synthetic FHIR data, and are already validated — the
generation step just moves upstream, from "run Synthea myself" to "MITRE ran
Synthea and published the result."

This is the kind of judgment call documented here on purpose: recognizing
when a tool's edge-case behavior isn't worth fighting, and choosing the
lower-risk path to the same outcome, rather than escalating time spent on a
non-essential step.

## Provenance

| Field | Value |
|---|---|
| Source | Synthea pre-generated sample synthetic patient records |
| Source URL | https://synthea.mitre.org/downloads |
| Format | FHIR R4 (JSON bundles), one bundle per patient |
| Ingestion method | Manual download and extraction |
| Ingestion date | See `downloaded_at` in `manifest.json` |
| File count / size | See `file_count` / `total_size_bytes` in `manifest.json` |

Exact provenance (source name, URL, download timestamp, file count, total
size) is recorded in [`manifest.json`](./manifest.json), generated by
`scripts/document_raw_source.py`. Per-file SHA-256 checksums are recorded in
[`checksums.sha256`](./checksums.sha256), in standard `sha256sum` format.

## Verifying integrity

To confirm the files on disk still match what was originally documented
(nothing corrupted, silently replaced, or partially re-extracted):

```bash
python scripts/document_raw_source.py --source-dir data/raw/synthea --verify
```

This exits non-zero and lists any missing, unexpected, or checksum-mismatched
files if the raw layer has drifted from its recorded manifest.

## Data classification

Classification: **public / synthetic** — no PII, no PHI, no real individuals.
Because this dataset simulates the *shape* of real clinical data (HL7 FHIR
resources, SNOMED CT / ICD-10 coded conditions and observations), it is
treated downstream with the same schema and quality rigor as if it were
sensitive, as a deliberate demonstration of governance practice — but it
carries none of the actual compliance obligations (LGPD/HIPAA/GDPR) that real
patient data would.

## Re-running ingestion (if you need a fresh copy)

1. Download a sample set from https://synthea.mitre.org/downloads (FHIR R4
   format; the 1K-patient set is a reasonable default for this project's
   scale).
2. Extract it into `data/raw/synthea/`.
3. Run `python scripts/document_raw_source.py --source-dir data/raw/synthea
   --source-url <url> --source-name "<name of the package you downloaded>"`
   to regenerate `manifest.json` and `checksums.sha256`.
